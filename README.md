# Pump Fleet Dashboard

A frontend-only dashboard for monitoring a fleet of oil-and-gas pumps. All data is synthetic — generated client-side from a deterministic seed — so the app runs as a pure static site with no backend.

Live demo: <https://landauer.github.io/pump-fleet-dashboard/> (after deploy)

## Quick start

```bash
npm install
npm run dev          # vite dev server
npm test             # vitest run (unit + integration)
npm run build        # production bundle in dist/
```

## What it does

- **Fleet overview** (`/`) — one card per pump with derived status (green / yellow / red / maintenance) computed from current alerts, latest readings, and a fleet summary bar.
- **Pump detail** (`/pump/$id`) — six live time-series charts (rotation speed, inlet/outlet pressure, flow rate, vibration, temperature) with selectable time windows (3 h / 24 h / 7 d / 31 d), an alerts incident list, work orders with create/edit/delete, and a maintenance schedule.
- **Live alert toaster** — a global Snackbar layer mounted at the root layout. When a metric crosses a threshold on any pump, a toast appears regardless of which page you're on. Multiple seeded incidents on the same pump collapse into one combined toast on page load to avoid a flood. **View pump** navigates with a `?from=alert` flag and surfaces a back chip; **Dismiss** closes the toast without acknowledging.
- **Incident-based alerts** — an alert represents a *period* during which a signal is out of bounds, with a start time, peak severity, current severity, and an end time when it returns to nominal. Acknowledging an incident silences future toasts but does **not** make the pump green if the metric is still bad.

## Synthetic data

Telemetry is generated by a seeded PRNG so reloads produce the same history. One pump (`pump-003`, "Charlie Injector") is configured with a worn-impeller drift pattern that's visually obvious on the charts — declining outlet pressure and flow rate, rising vibration and temperature, while rotation speed stays normal. The status badge for that pump turns red because alert rules pick it up, not because anything is hardcoded.

A `setInterval` ticks every 5 s, appends a new telemetry point to each cached window, and runs alert rules to open / escalate / resolve incidents.

## Architecture

```text
src/
├── domain/          pure TypeScript, zero React imports — easy to unit-test
│   ├── models.ts    Pump, TelemetryPoint, Alert (incident), WorkOrder, thresholds
│   ├── generators/  seeded telemetry generation + degraded-pump drift
│   ├── alerts/      threshold rules engine
│   └── store.ts     in-memory FleetStore with pub/sub + alert-event channel
├── hooks/           React bridge (useFleetStore, useStoreSnapshot, useLiveTick)
├── components/
│   ├── alerts/      LiveAlertToaster (root-mounted)
│   ├── detail/      AlertList, TelemetryChart, WorkOrderList/Form, …
│   ├── layout/      Sidebar, TopBar
│   └── list/        PumpCard, SummaryStatsBar
├── routes/          TanStack Router file-based routes (__root, index, pump.$id)
└── utils/           formatters (timestamps, durations, alert messages)
```

Domain layer has no UI dependencies, which is why most of the test suite is plain Vitest. UI components are thin wrappers around store reads.

## Tech stack

Vite 8 · React 19 · TypeScript · MUI 9 · TanStack Router · Recharts · Vitest + React Testing Library

## Tests

```bash
npm test                 # one-shot
npm run test:watch       # watch mode
npm run test:coverage    # v8 coverage with 80 % thresholds enforced in vite.config.ts
```

## Deploy (GitHub Pages)

`vite.config.ts` sets `base: '/pump-fleet-dashboard/'`, so `npm run build` produces a `dist/` ready to publish at `https://<user>.github.io/pump-fleet-dashboard/`. Push the built `dist/` (or wire up a GitHub Actions workflow that runs `npm ci && npm run build` and deploys to the `gh-pages` branch).
